# AutoSaveRestart

AutoSaveRestart 是一个适用于 **MCDReforged** 的 Minecraft 服务器自动保存与自动重启插件，默认针对 **1.7.10 系服务端（Thermos 及其分支 Crucible，GTNH 整合包即使用 Crucible）** 做了适配。配置文件与全部提示均为中文。

> 本仓库文档与源码注释的写法遵循 [doc/注释与Markdown规范.md](doc/注释与Markdown规范.md)。

## 功能

- 按设定间隔自动保存服务器地图，保存前发送全服预警与逐秒倒计时
- **崩溃守护**：服务端进程退出（崩溃、控制台执行 `stop`、定时重启）后自动拉起
- **定时重启**：按设定周期执行「保存 → 倒计时 → 停止服务端 → 自动拉起」
- **打断重启**：一条指令取消待执行的重启
- **预约重启 / 预约关服**：`restart 30m`、`shutdown 1h30m` 先播报，再按剩余时间折半提醒，到点执行
- **临时延后**：把下一次重启往后推，支持 `h`/`m`/`s` 任意组合；未启用定时重启时按「预约一次重启」生效
- 管理员可查看状态、手动保存、手动重启、取消流程、修改保存间隔
- 崩溃循环保护：短时间内反复崩溃时暂停拉起，避免无意义地反复重启
- 配置文件全中文，文件内附逐项说明；首次使用自动生成

## 使用要求

- MCDReforged 2.14.0 或更高版本
- Minecraft Java 版服务端

崩溃守护依赖 MCDR 的 `set_exit_after_stop_flag` 接口。若当前 MCDR 不提供该接口，插件会在日志中提示，此时 MCDR 会随服务端一同退出，守护无法生效，只能改由启动脚本的循环完成重启。验证环境为 MCDR 2.16.2，该接口可用。

## 安装

1. 下载最新版 `AutoSaveRestart-v版本号.mcdr`。
2. 将文件放入 MCDReforged 的 `plugins` 文件夹。
3. 重启 MCDReforged，或者重新加载插件。
4. 插件首次加载后会自动生成配置文件：

```text
config/autosave/config.json
```

安装完成后，插件会按照默认设置自动运行。

### 部署注意

- 启动脚本**不要**用 `:loop` / `goto loop` 之类的循环包裹 MCDR。守护开启后 MCDR 会常驻运行，循环只会在执行 `shutdown` 之后把 MCDR 重新拉起，导致无法真正停机。
- 启动脚本建议在 MCDR 退出后保留窗口（`pause`），便于查看异常堆栈。
- 与其它按固定时刻重启的插件（例如每天定时执行 `stop` 的插件）同时启用时，确认两者的重启时刻不会叠加。插件自身的定时重启由 `定时重启间隔分钟` 控制，默认关闭。

## 工作原理

### 自动保存

1. 每 30 分钟自动保存一次。
2. 距离保存 60 秒时向全服发送金色预警。
3. 最后 10 秒开始逐秒倒计时。
4. 最后 5 秒变为红色加粗提示。
5. 保存开始时显示浅蓝色提示。
6. 保存完成后显示绿色提示。

### 自动重启

崩溃守护开启时，插件要求 MCDR 在服务端进程退出后保持运行，并在「拉起延迟秒数」之后调用 MCDR 的启动接口重新拉起服务端。因此以下三种情况都会自动拉起：

- 服务端崩溃，进程以非 0 返回码退出
- 在控制台、游戏内或 RCON 执行 `stop`
- 插件执行定时重启或手动重启

只有先执行 `shutdown` 或 `guard off` 关闭守护，停止服务端才不会自动拉起。

定时重启间隔为 0 时关闭定时重启，仅保留崩溃守护。

### 崩溃循环保护

- 服务端在启动阶段（尚未输出 `Done`）退出，按启动失败计数，连续 2 次后暂停拉起。
- 进入 `Done` 后以非 0 返回码退出，按崩溃计数；在「崩溃统计窗口分钟」内达到「崩溃次数上限」后暂停拉起。
- 正常 `stop`（返回码 0）只触发重启，不计入崩溃次数。
- 暂停后执行 `guard on` 可清零计数并恢复。

## 管理命令

默认情况下，以下命令仅管理员或控制台可以使用。命令前缀默认为 `!!autosave`，别名 `!!as`。

| 命令 | 作用 |
| --- | --- |
| `!!autosave` | 查看当前状态 |
| `!!autosave help` | 输出完整使用说明 |
| `!!autosave run` | 立即执行一次保存流程 |
| `!!autosave restart` | 立即执行一次重启流程 |
| `!!autosave restart <时长>` | 预约重启，到点前按剩余时间折半播报提醒 |
| `!!autosave cancel` | 取消正在进行的保存或重启流程 |
| `!!autosave interrupt` | 打断本次自动重启 |
| `!!autosave delay <时长>` | 把下一次定时重启往后推 |
| `!!autosave set <分钟>` | 修改自动保存间隔 |
| `!!autosave guard on` | 开启崩溃守护并清零计数 |
| `!!autosave guard off` | 关闭崩溃守护 |
| `!!autosave start` | 手动启动服务端进程 |
| `!!autosave shutdown` | 关闭崩溃守护并正常关服 |
| `!!autosave shutdown <时长>` | 预约关服，到点前按剩余时间折半播报提醒 |

### 查看状态

```text
!!autosave
```

输出内容包含：当前阶段、下一次自动保存剩余时间、下一次自动重启剩余时间、崩溃守护状态、统计窗口内异常退出次数、上次服务端退出码、是否处于逐秒倒计时。

### 输出完整说明

```text
!!autosave help
```

输出全部子命令、时长写法、自动重启规则与配置文件位置，适合首次部署时对照使用。

### 手动保存与手动重启

```text
!!autosave run
!!autosave restart
!!autosave restart 30m
```

都会执行完整流程：

```text
预警 → 静默等待 → 逐秒倒计时 → 保存 → （重启时）停止服务端 → 自动拉起
```

不带时长时立即开始；带时长时先进入预约等待，见上一节的播报规则。

已有流程进行中时不会重复开启。

### 预约重启与预约关服

给 `restart` 或 `shutdown` 带上时长，指令不会立即执行，而是进入预约等待：

```text
!!autosave restart 30m
!!autosave shutdown 1h30m
```

等待期间按「剩余时间减半」的节奏向全服播报。以 `restart 30m` 为例：

| 距停止时刻 | 播报内容 |
| --- | --- |
| 30分钟 | 管理员发起了重启，服务器将在 30分钟 后重启 |
| 15分钟 | 距离重启还有 15分钟 |
| 7分钟30秒 | 距离重启还有 7分钟30秒 |
| 3分钟45秒 | 距离重启还有 3分钟45秒 |
| 1分钟52秒 | 距离重启还有 1分钟52秒 |

剩余时间降到「保存预警秒数」（默认 60 秒）后停止折半播报，转入正式流程：

```text
预警 → 静默等待 → 逐秒倒计时 → 保存 → 停止服务端
```

因此指定的时长是「距服务端停止的时刻」，而不是「距流程开始的时刻」。

其他规则：

- 预约时长短于预警秒数时，预警与倒计时按实际时长缩短，停止时刻不会被拖后。例如 `restart 30s` 就在 30 秒后停止。
- 预约期间仍按「保存间隔分钟」自动保存，长时预约（如 2 小时）不会中断保存节奏。
- 等待期间可以用 `cancel` 或 `interrupt` 取消，全服会收到取消提示，服务端继续正常运行。
- `shutdown <时长>` 到点时才关闭崩溃守护并停服，中途取消不影响守护状态。

### 取消流程

```text
!!autosave cancel
```

取消正在进行的保存或重启流程，全服会收到红色取消提示，下一轮排期照常进行。

### 打断自动重启

```text
!!autosave interrupt
```

根据当前所处阶段产生两种效果：

- 重启流程正在进行（预警、静默等待、倒计时阶段）：取消本次重启，本轮跳过，下一个重启周期照常生效。
- 服务端已停止、正在等待「拉起延迟秒数」结束：取消本次拉起，服务端保持停止状态，可用 `!!autosave start` 手动启动。

当前没有待执行的重启时，指令会明确提示。

### 临时延后下一次重启

```text
!!autosave delay <时长>
```

把下一次自动重启的时间点整体往后推指定时长，不修改配置文件，重新加载插件后恢复。例如：

```text
!!autosave delay 2h
!!autosave delay 45m
!!autosave delay 1h30m
!!autosave delay 1h30m15s
```

两种生效方式：

- 已启用定时重启（`定时重启间隔分钟` 大于 0）：在现有时间点的基础上累加，重复执行可继续推迟。
- 未启用定时重启：从当前时刻起算，在该时长后自动重启一次，效果等同于预约一次重启。再次执行会在上一次的基础上继续累加。

若重启流程已经开始，执行该指令会静默取消当前流程并按新的时间点重排，不向全服播报取消提示。

### 修改自动保存间隔

```text
!!autosave set <分钟>
```

例如 `!!autosave set 60` 表示将自动保存间隔修改为 60 分钟，修改结果写入配置文件。

### 崩溃守护开关

```text
!!autosave guard on
!!autosave guard off
```

`guard on` 会同时清零崩溃计数与启动失败计数，用于从暂停状态恢复。`guard off` 只影响本次运行，重新加载插件后恢复配置文件中的 `崩溃守护` 值。

### 真正关服

```text
!!autosave shutdown
!!autosave shutdown 30m
```

关闭崩溃守护并停止服务器，停止后不会自动拉起。这是唯一推荐的停机方式；直接执行 `stop` 会被守护重新拉起。

不带时长时立即停服；带时长时先播报并等待，到点后保存再停服。

### 手动启动

```text
!!autosave start
```

服务端已停止（例如刚执行过 `interrupt`）时手动启动进程，同时取消可能仍在等待的守护拉起，避免重复启动。

## 时长写法

| 单位 | 可用写法 |
| --- | --- |
| 小时 | `h`、`小时`、`时` |
| 分钟 | `m`、`分钟`、`分` |
| 秒 | `s`、`秒` |

规则：

- 三个单位可单独使用，也可任意组合，顺序不影响结果。
- 只写数字时按分钟计算，`delay 30` 等同于 `delay 30m`。
- 允许空格与全角逗号作为分隔，`1 小时 30 分` 与 `1小时30分` 等价。
- 单次时长上限为 30 天。
- `restart`、`shutdown`、`delay` 三个指令共用这套写法。

## 配置文件

配置文件位置：

```text
config/autosave/config.json
```

全部配置项为中文，文件内的 `配置说明` 字段逐项写明用途与取值范围。常用配置：

| 配置项 | 作用 | 默认值 |
| --- | --- | --- |
| `保存间隔分钟` | 自动保存间隔，单位分钟，最小 1 | `30` |
| `保存预警秒数` | 提前多少秒发送预警，0 表示不发送 | `60` |
| `保存倒计时秒数` | 最后多少秒逐秒倒计时，0 表示不倒计时 | `10` |
| `保存指令` | 保存时执行的指令 | `save-all` |
| `播报方式` | `say` 或 `tellraw` | `say` |
| `崩溃守护` | 服务端退出后是否自动拉起 | `true` |
| `拉起延迟秒数` | 退出后等待多少秒再拉起，0 表示立即 | `5` |
| `定时重启间隔分钟` | 定时重启周期，0 表示关闭 | `0` |
| `崩溃次数上限` | 统计窗口内允许的异常退出次数，0 表示不限制 | `3` |
| `崩溃统计窗口分钟` | 异常退出统计窗口长度 | `10` |
| `重启指令` | 自动重启时发送给服务端的指令 | `stop` |
| `主指令` | 管理指令名称 | `!!autosave` |
| `指令别名` | 管理指令别名列表 | `["!!as"]` |
| `权限等级` | 管理指令所需权限等级 | `3` |
| `提示文字` | 播报与回复文案 | 见下节 |

修改后重新加载插件生效；`set` 指令只修改保存间隔并立即写回。

## Thermos / GTNH / 1.7.10 适配

插件只使用 MCDR 层接口，与具体服务端核心无关，Thermos 与 Crucible（GTNH 使用的 Thermos 分支）上的行为一致。以下为 1.7.10 环境的注意事项。

- **提示使用原生 `say` 指令**：`播报方式` 默认为 `say`，插件将颜色转换为 `§` 码后执行
  `say §6文本§r`，不依赖 `tellraw` 的 JSON，也不受 GTNH 聊天格式化模组影响。
  如需 RText 富文本，将 `播报方式` 改为 `tellraw`。
- **仅使用 16 色**：1.7.10 不支持 RGB / hex，颜色固定映射到 `§0`–`§f`，加粗使用 `§l`。
- **单行发送**：提示文本中的换行会被压缩为空格，避免一条 `say` 被控制台拆分为两条命令。
- **编码**：MCDR 的 `config.yml` 中 `encoding` / `decoding` 保持 `utf8`，服务端启动参数需包含
  `-Dfile.encoding=UTF-8`（GTNH 整合包启动脚本通常已包含），否则中文提示会乱码。
- **服务端未运行时跳过**：GTNH 启动耗时较长，服务器未运行时插件会跳过本轮并重新计时，
  不会向尚未启动的控制台发送指令。
- **`save-all` 可能造成短暂停顿**：GTNH 世界体积较大，保存瞬间可能出现 TPS 波动，预警文案已提示玩家；
  保存间隔不建议低于 15 分钟。
- **`say` 输出带 `[Server]` 前缀**：这是 1.7.10 原版行为，如需去除可改用 `tellraw` 模式。
- **拉起延迟**：GTNH 退出时需落盘，端口释放也可能滞后。插件在拉起失败时会以 5 秒间隔重试，最多 3 次。
  若服务端经常在端口释放前被拉起，可把 `拉起延迟秒数` 调大。

## 更新记录

### 1.3.4

- 修复：执行 `restart` / `cancel` / `interrupt` / `delay`，或服务端退出、修改保存间隔时，
  控制台会打印一段 `InvalidStateError: CANCELLED` 与 `Exception in callback ...` 的堆栈。
  原因是插件取消了 `schedule_task` 返回的 future：MCDR 的取消不会传导到 asyncio 协程，
  协程随后正常结束时 `future_utils.copy_done_state` 又对已取消的 future 调用 `set_result`。
  现在不再取消周期协程，退出改由 generation 与取消标志驱动，最长延迟一个轮询间隔（1 秒）。
- 该堆栈只影响日志可读性，不影响保存与重启行为。

### 1.3.3

- 取消回执改为「【自动保存】已取消本次操作。」，不再拼接原因，
  避免出现「已取消本次操作：管理员 已取消本次操作」这种重复表述。
- 从 1.2.x 升级时若「提示文字」里仍保留旧文案（帮助、当前流程、流程进行中、
  无法取消、取消原因），建议手动替换为 1.3.x 的默认值，这些条目已扩展到重启与关服。

### 1.3.2

- 修复：`interrupt` 打断 `delay` 预约的一次性重启后，排期会被立即重新捡回来，
  提示「已打断」但状态里重启时间仍在。定时重启未启用时改为直接清空排期。

### 1.3.1

- 修复：在「预警后的静默等待」阶段执行 `cancel` 不生效、也没有任何回执，
  服务端仍会照常保存并重启。原因是分段睡眠只检查插件卸载，未检查取消标志。
- 修复：预约流程转入正式流程后重复收尾，可能重复排期。
- `cancel` 成功后补一条回执「已取消本次操作」，不再静默。

### 1.3.0

- 新增 `restart <时长>` / `shutdown <时长>` 预约执行，按剩余时间折半播报。
- 新增 `shutdown <时长>` 预约关服，到点才关闭崩溃守护。

## 从 1.1.x 升级

旧版配置使用英文键名，插件加载时会自动迁移为中文键名并写回配置文件，无需手动修改。
迁移只搬运取值，不会覆盖已经手写的中文键。旧版没有的重启相关配置按默认值补齐，其中 `定时重启间隔分钟` 默认为 0，升级后不会自动开始定时重启。

从 1.2.x 升级到 1.3.0 时，「提示文字」中新增的预约播报、预约关服与取消文案会自动按默认值补全，已修改过的旧条目保持原样。

## 权限

默认管理命令权限等级为 `3`，即 MCDReforged 管理员权限。

服务器控制台可以直接使用全部管理命令。

## 更新插件

下载新版 `.mcdr` 文件后，替换 `plugins` 文件夹中的旧版本，然后重新加载插件即可。

建议保留已有的配置文件：

```text
config/autosave/config.json
```
